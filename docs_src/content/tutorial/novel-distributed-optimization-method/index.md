# Novel Distributed Optimization Method

While [Tutorial > Problem Definition and Algorithm Execution](../problem-definition-and-algorithm-execution/index.md) shows how to *use* an existing coordination method to solve a distributed design optimization problem, this section is written for developers who want to *extend* the abbr:DDO framework with a **novel distributed optimization method**.

The framework is built around a single [Unified Algorithmic Structure](../../distributed-optimization-for-multidisciplinary-design/unified-algorithmic-structure.md): every coordination method â€” [abbr:ALC](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/augmented-lagrangian-coordination.md), [abbr:ALADIN](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/aladin.md), [abbr:SBDP](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/sensitivity-based-distributed-programming.md), and [Consensus abbr:ALC](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/consensus-augmented-lagrangian-coordination.md) â€” is a specialization of it. Adding a new method therefore means providing method-specific classes that plug into the shared machinery, rather than writing the entire method from scratch. Further conceptual background is given in [Framework Architecture > Core Components and Unified Algorithmic Structure](../../framework-architecture/core-components-and-unified-algorithmic-structure.md).

## 1. Casting the novel distributed optimization method into the Unified Algorithmic Structure

Before writing any code, the novel distributed optimization method is expressed in terms of the [Unified Algorithmic Structure](../../distributed-optimization-for-multidisciplinary-design/unified-algorithmic-structure.md).

When casting the novel distributed optimization method into the unified structure, the following aspects specifically need to be considered, as each determines which of the later building blocks actually need to be defined:

- **The coupling information sym:u that is exchanged.** The framework already supports mapped responses ${}^{j}_{i}$sym:H, coupling variables ${}^{j}_{i}$sym:h, shared design variables ${}^{i}_{j}$sym:z, and target shared design variables. A novel distributed optimization method may additionally exchange penalty weights, Lagrange multipliers, or auxiliary variables etc. This drives [Section 2](#2-defining-the-middlelevel-and-couplingparameters-classes).
- **Whether each coupling is symmetric or asymmetric.** A *peer* coupling between two subsystems is **symmetric** â€” both ends play the same role and exchange the *same kind* of information, so a **single** coupling class (subclassing [`SubSysCouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md)) and a **single** middlelevel coupling class (subclassing [`SubSysMiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md)) serve both sides, as in [abbr:ALC](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/augmented-lagrangian-coordination.md) and [Consensus abbr:ALC](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/consensus-augmented-lagrangian-coordination.md). A coupling to a *controller* may be **asymmetric** â€” the information a subsystem sends to the controller differs from what the controller returns, requiring **separate** classes per direction that are combined in one storage class, as in [abbr:ALADIN](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/aladin.md) (see [Section 2](#2-defining-the-middlelevel-and-couplingparameters-classes)).
- **Whether there is a controller problem.** Methods such as [abbr:ALADIN](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/aladin.md) add a central controller; methods such as [abbr:ALC](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/augmented-lagrangian-coordination.md) do not. This decides whether controller-side classes are needed in [Sections 2](#2-defining-the-middlelevel-and-couplingparameters-classes), [3](#3-defining-the-coordination-specific-subsystem-classes) and [5](#5-implementing-the-coordination-method-entry-point).
- **Where the coupling parameters are updated.** In the inner loop, the outer loop, or both â€” this governs which update hooks are overridden in [Section 3](#3-defining-the-coordination-specific-subsystem-classes) and which update strategy is selected in [Section 4](#4-reusing-or-defining-convergence-iteration-scheme-and-update-classes).

## 2. Defining the middlelevel and couplingparameters classes

A coupling has two complementary representations. The [`middlelevel`](../../api/Distributed_Design_Optimizer/middlelevel/index.md) package implements the **interface storage** through which subsystems exchange coupling information across process boundaries, while the [`couplingparameters`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/index.md) package holds the *subsystem-local* view of each coupling. Every subsystem keeps a list of `CouplingParameters<Method>` instances â€” one per pairwise coupling with a neighbor â€” and copies values to and from the shared `MiddleLevelCoupling<Method>`. This division of labor, and the copy mechanics that connect the two, are described in detail in [Framework Architecture > Information Sharing via CouplingParameters and MiddleLevelDataStorage](../../framework-architecture/information-sharing-via-couplingparameters-and-middleleveldatastorage.md). The full inheritance structure of the classes subclassed below is shown on [`middlelevel`](../../api/Distributed_Design_Optimizer/middlelevel/index.md) and [`couplingparameters`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/index.md) API reference pages.

For a novel distributed optimization method, a sub-package [`middlelevel`](../../api/Distributed_Design_Optimizer/middlelevel/index.md)`/<method>/` is added, containing:

- `MiddleLevelDataStorage<Method>` â€” the shared storage slot for one pairwise coupling, subclassing [`MiddleLevelDataStorageBasis`](../../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelDataStorageBasis.md). Its `__init__` populates a `_couplingdata` list with one `MiddleLevelCoupling<Method>` per side of the coupling.
- `MiddleLevelCoupling<Method>` â€” the container holding the actual values exchanged for one side of a **symmetric peer coupling** between two local subsystems, subclassing [`SubSysMiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md) (in turn a [`MiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelCouplingBasis.md)). The base class already stores the four standard quantities (mapped responses, coupling variables, shared and target shared design variables).
- If the method has a controller, the controller-side middlelevel coupling classes need to be defined. When the controller exchange is *asymmetric* (as in [abbr:ALADIN](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/aladin.md)), this splits into **separate directional classes** â€” a local-to-controller [`LocalToController_MiddleLevelCouplingALADIN`](../../api/Distributed_Design_Optimizer/middlelevel/aladin/LocalToController_MiddleLevelCouplingALADIN.md) and a controller-to-local [`ControllerToLocal_MiddleLevelCouplingALADIN`](../../api/Distributed_Design_Optimizer/middlelevel/aladin/ControllerToLocal_MiddleLevelCouplingALADIN.md), both subclassing [`LocalController_MiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/LocalController_MiddleLevelCouplingBasis.md) (in turn a [`MiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelCouplingBasis.md)) â€” combined in one [`LocalController_MiddleLevelDataStorageALADIN`](../../api/Distributed_Design_Optimizer/middlelevel/aladin/LocalController_MiddleLevelDataStorageALADIN.md) storage class, mirroring the directional couplingparameters classes below.
- `InConsistencySize` â€” declares the sizes of the inconsistency vectors for this method, subclassing [`InConsistencySizeBasis`](../../api/Distributed_Design_Optimizer/middlelevel/InConsistencySizeBasis.md).

and, in the [`couplingparameters`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/index.md)`/<method>/` package, the following are defined:

- `CouplingParameters<Method>` â€” the subsystem-local view of a **symmetric peer coupling** between two local subsystems, subclassing [`SubSysCouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md) (in turn a [`CouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersBasis.md) / [`CouplingParametersInterface`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersInterface.md)).
- If the method has a controller, the controller-side coupling parameters need to be defined. When the controller exchange is *asymmetric* (as in [abbr:ALADIN](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/aladin.md)), this splits into **separate directional classes** â€” a local-side [`LocalToController_CouplingParametersALADIN`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/aladin/LocalToController_CouplingParametersALADIN.md) for what a subsystem sends to the controller, and a controller-side [`ControllerCouplingParametersALADIN`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/aladin/ControllerCouplingParametersALADIN.md) (subclassing [`ControllerCouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/ControllerCouplingParametersBasis.md)) â€” mirroring the directional middlelevel classes above.

The four standard coupling quantities â€” mapped responses, coupling variables, shared design variables, and target shared design variables â€” are defined **once** in [`SubSysCouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md) (and mirrored in [`SubSysMiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md)), with every method-specific subclass only *adding to* this base rather than redeclaring them. These four quantities are exactly what is needed to express and post-process the inconsistencies between neighboring local subsystems (see [Data Logging](../../framework-architecture/data-logging.md) and [Processing](../../tutorial/processing/index.md)), so they are common to *every* coordination method; a novel distributed optimization method adds only the *extra* information (penalty weights, Lagrange multipliers, auxiliary or sensitivity quantities) that its own coordination scheme requires on top.

By convention the couplingparameters attributes mirror the naming of the matching `MiddleLevelCoupling<Method>` class. In addition, each `CouplingParameters<Method>` holds a set of `_copy_*` attributes that store the data *pulled from the middle level* (i.e. the neighbor's values). The mapping between the two is realized by subclassing [`CouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersBasis.md) with a method-specific class and implementing the two copy procedures:

- `CopyFromMiddleLevelCoupling(middlelevelcouplingIn)` â€” read the neighbor's shared values out of the middle level into the local `_copy_*` attributes.
- `CopyToMiddleLevelCoupling(middlelevelcouplingIn)` â€” write this subsystem's own values into the middle level for the neighbor to read.

A key design point is that a `CouplingParameters<Method>` class may hold information that is **never written to the shared middle level** â€” it stays local to the subsystem but remains associated with a specific neighbor. What is and is not communicated is decided entirely by `CopyToMiddleLevelCoupling()` and `CopyFromMiddleLevelCoupling()`.

The three existing methods illustrate how much a method's classes add beyond their basis parent, and whether that extra information is shared:

- [abbr:ALC](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/augmented-lagrangian-coordination.md) relies on a **symmetric** coupling and information exchange with its neighboring subsystems. Its [`CouplingParametersALC`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/alc/CouplingParametersALC.md) extends [`SubSysCouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md) with penalty weights and Lagrange multipliers, which are â€” however â€” not communicated to neighbors. Consequently its [`MiddleLevelCouplingALC`](../../api/Distributed_Design_Optimizer/middlelevel/alc/MiddleLevelCouplingALC.md) adds nothing beyond [`SubSysMiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md).
- [Consensus abbr:ALC](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/consensus-augmented-lagrangian-coordination.md) relies on a **symmetric** coupling and information exchange with its neighboring subsystems. Its [`CouplingParametersConsensusALC`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/consensus_alc/CouplingParametersConsensusALC.md) extends [`SubSysCouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md) with several quantities, some of which are communicated to neighbors. Consequently, its [`CouplingParametersConsensusALC`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/consensus_alc/CouplingParametersConsensusALC.md) holds corresponding `_copy_` attributes and its [`MiddleLevelCouplingConsensusALC`](../../api/Distributed_Design_Optimizer/middlelevel/consensus_alc/MiddleLevelCouplingConsensusALC.md) extends [`SubSysMiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md) with the same quantities.
- [abbr:ALADIN](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/aladin.md) relies on an **asymmetric** coupling and information exchange with the controller subsystems, so a single class cannot represent both ends: a subsystem-to-controller class packages the sensitivity data sent to the controller ([`LocalToController_CouplingParametersALADIN`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/aladin/LocalToController_CouplingParametersALADIN.md) / [`LocalToController_MiddleLevelCouplingALADIN`](../../api/Distributed_Design_Optimizer/middlelevel/aladin/LocalToController_MiddleLevelCouplingALADIN.md)), while a controller-to-subsystem class returns the coordination step ([`ControllerCouplingParametersALADIN`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/aladin/ControllerCouplingParametersALADIN.md) / [`ControllerToLocal_MiddleLevelCouplingALADIN`](../../api/Distributed_Design_Optimizer/middlelevel/aladin/ControllerToLocal_MiddleLevelCouplingALADIN.md)). Both directions are combined in one storage class ([`LocalController_MiddleLevelDataStorageALADIN`](../../api/Distributed_Design_Optimizer/middlelevel/aladin/LocalController_MiddleLevelDataStorageALADIN.md)). Crucially, [abbr:ALADIN](../../distributed-optimization-for-multidisciplinary-design/coordination-methods/aladin.md) still also uses [`SubSysCouplingParametersBasis`](../../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md) and [`SubSysMiddleLevelCouplingBasis`](../../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md) for coupling with neighboring local subsystems. This is not necessary for the coordination method itself, but enables computing and post-processing the inconsistencies between neighboring local subsystems (see [Data Logging](../../framework-architecture/data-logging.md) and [Processing](../../tutorial/processing/index.md)). A novel distributed optimization method should therefore keep these peer middlelevel and couplingparameters classes even when â€” like ALADIN â€” its algorithm does not otherwise communicate between local subsystems.

## 3. Defining the coordination-specific subsystem classes

The [`subsystem`](../../api/Distributed_Design_Optimizer/subsystem/index.md) package represents an individual processing unit. For a novel distributed optimization method, the following are defined:

- `LocalSubSystem<Method>`, subclassing [`LocalSubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) (in turn a [`SubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/SubSystemBasis.md) / [`SubSystemInterface`](../../api/Distributed_Design_Optimizer/subsystem/SubSystemInterface.md)). Its `__init__` must set the attributes that the base classes leave uninitialized (marked *to be initialized in child-class* in the base `__init__`):
    - `_couplingparameters` â€” the list of `CouplingParameters<Method>` instances (one per neighbor) defined in [Section 2](#2-defining-the-middlelevel-and-couplingparameters-classes). This must be assigned **before** calling `super().__init__()`, because the base initialization of the optimization data already relies on it.
    - `_inconsistencies` â€” a list of `InConsistencySize` (one per coupling parameter), assigned after `super().__init__()`.
    - `_local_convergenceindicator_innerloop` and `_local_convergenceindicator_outerloop` â€” the inner- and outer-loop convergence indicators, taken from the `__init__` arguments (see [Section 4](#4-reusing-or-defining-convergence-iteration-scheme-and-update-classes)).
    - `_updatecouplingparametermethod_outerloop` â€” the outer-loop coupling-parameter update method, also taken from the `__init__` arguments (see [Section 4](#4-reusing-or-defining-convergence-iteration-scheme-and-update-classes)).

    It is furthermore **strongly recommended** that the `__init__` also declares **compatibility lists** and validates the inputs using a newly defined `validate_inputs()`. `self.validate_inputs()` is called as the **last** statement of `__init__`, once all the attributes it inspects are set.

    It must also implement the two methods that [`LocalSubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) leaves abstract â€” and that only local subsystems provide â€” namely `return_initialized_Inconsistencies()` and `append_Controller()`.

- If the method utilizes a single controller, additionally a `ControllerSubSystem<Method>` subclassing [`ControllerSubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/ControllerSubSystemBasis.md) â€” as done by [`ControllerSubSystemALADIN`](../../api/Distributed_Design_Optimizer/subsystem/ControllerSubSystemALADIN.md).


Furthermore the `LocalSubSystem<Method>` and `ControllerSubSystem<Method>` (if existing) need to define the following methods, each of which implements a specific step of [Algorithm 5](../../distributed-optimization-for-multidisciplinary-design/unified-algorithmic-structure.md#algorithm-5) and of the per-subsystem solve [`run_IterativeOptimization()`](../../framework-architecture/subsystem-optimization.md):

- `prepare_OptimizationProblem()` and `postprocess_Optimization()` â€” the *"Prepare optimization problem formulation"* and *"Post-process the optimization"* steps that bracket the `argmin` in [Algorithm 5](../../distributed-optimization-for-multidisciplinary-design/unified-algorithmic-structure.md#algorithm-5). `prepare_OptimizationProblem()` assembles the concrete problem to be solved from the coupling parameters just read from the middle level and other necessary information available in the `LocalSubSystem<Method>` or `ControllerSubSystem<Method>`.
- `evaluateCoordinationObjective()`, `evaluateCoordinationEqualityConstraint()`, `evaluateCoordinationInequalityConstraint()` â€” the ${}^{i}$sym:P and ${}^{i}$sym:Q terms of [Algorithm 5](../../distributed-optimization-for-multidisciplinary-design/unified-algorithmic-structure.md#algorithm-5). These are the coordination-specific additions that [`run_IterativeOptimization()`](../../framework-architecture/subsystem-optimization.md) combines with the local objective ${}^{i}$sym:v_f and constraints ${}^{i}$sym:v_g & ${}^{i}$sym:v_h (in case of `LocalSubSystem<Method>`); `ControllerSubSystem<Method>` only has coordination-related terms.
- `evaluate_Inconsistencies()` (only for `LocalSubSystem<Method>`, not `ControllerSubSystem<Method>`) â€” computes the inconsistency $^{i}_{j}$sym:c and $^{j}_{i}$sym:c and other related quantities.
- `mapToController()` (only relevant when the method has a controller) â€” in a `LocalSubSystem<Method>`, it is implemented to map the subsystem's own information into the local-to-controller coupling parameters ${}^{i}_{C}$sym:u sent to the controller (see [Section 2](#2-defining-the-middlelevel-and-couplingparameters-classes)). If the method has no controller, it is left a no-op (`pass`). A `ControllerSubSystem<Method>` never maps to itself, so it does not need to implement this at all â€” the required no-op is already inherited from [`ControllerSubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/ControllerSubSystemBasis.md).
- `initializeCouplingParameters_before_CopyToMiddleLevel()`, `initializeCouplingParameters_after_CopyFromMiddleLevel()`, `initializeCouplingParameters_after_Second_CopyFromMiddleLevel()` â€” populate the coupling-parameter containers at start-up so that the very first exchange through the middle level is well-defined (the *"initial relevant coupling parameters in interface storage"* required by [Algorithm 5](../../distributed-optimization-for-multidisciplinary-design/unified-algorithmic-structure.md#algorithm-5)).
- `prepare_updateCouplingParameters()`, `updateCouplingParameters_innerLoop()`, `updateCouplingParameters_outerLoop()` â€” the *"Update relevant coupling parameters"* steps of [Algorithm 5](../../distributed-optimization-for-multidisciplinary-design/unified-algorithmic-structure.md#algorithm-5). They advance the method's relevant coupling parameters (e.g. penalty weights and Lagrange multipliers). Which of these are implemented is dictated by *where the coupling parameters are updated* ([Section 1](#1-casting-the-novel-distributed-optimization-method-into-the-unified-algorithmic-structure)).

The parent classes [`SubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/SubSystemBasis.md), [`LocalSubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md), and [`ControllerSubSystemBasis`](../../api/Distributed_Design_Optimizer/subsystem/ControllerSubSystemBasis.md) already provide standardized attributes and methods to realize the following functionalities:

- **History saving and data logging** â€” `appendtohistory()`, `savesubsystemhistory()`. See [Data Logging](../../framework-architecture/data-logging.md).
- **Derivative information** â€” finite-difference Jacobians as well as gradients, Jacobians, and Hessians of the local/total objective and constraints. See [Derivative Computation](../../framework-architecture/derivative-computation.md).
- **Lagrange multipliers of the local and coordination constraints** â€” `compute_KKT_system_matrix_and_bounds()`, `compute_KKT_multipliers()`, `compute_ApproximateKKT_multipliers()`, `decompose_KKT_multipliers()`. See [SubSystem Optimization > Multiplier reconstruction when the solver does not provide them](../../framework-architecture/subsystem-optimization.md#multiplier-reconstruction-when-the-solver-does-not-provide-them).
- **Iterative optimization** â€” the full local solve loop `run_IterativeOptimization()`, `runAnalysis()`, `mapToCouplingParameters()`, and total-objective/constraint evaluation. See [SubSystem Optimization](../../framework-architecture/subsystem-optimization.md).

This is why a new method only needs to supply the coordination-specific methods above.

## 4. Reusing or defining convergence, iteration scheme, and update classes

Three [`coordination`/](../../api/Distributed_Design_Optimizer/coordination/index.md) sub-packages provide interchangeable strategies for convergence criteria, innerloop iteration schemes and updating penalty weights or multipliers etc. In most cases **an existing class can be reused** and simply passed to the coordination method in [Section 5](#5-implementing-the-coordination-method-entry-point). A bespoke class is only defined when the novel distributed optimization method genuinely needs new behavior, in which case the relevant interface is subclassed, following the existing sister classes.

- [`convergence/`](../../api/Distributed_Design_Optimizer/coordination/convergence/index.md) â€” inner- and outer-loop convergence criteria. New criteria implement the factory [`ConvergenceIndicator_Innerloop_Interface`](../../api/Distributed_Design_Optimizer/coordination/convergence/ConvergenceIndicator_Innerloop_Interface.md) / [`ConvergenceIndicator_Outerloop_Interface`](../../api/Distributed_Design_Optimizer/coordination/convergence/ConvergenceIndicator_Outerloop_Interface.md) (methods `createLocalConvergenceIndicator()`, `createCentralizedConvergenceIndicator()`, `validate_inputs()`, `print_startup_summary()`, `print_termination_summary()`). 
- [`innerloop_iterationscheme/`](../../api/Distributed_Design_Optimizer/coordination/innerloop_iterationscheme/index.md) â€” how executions of local subsystems (and a controller) are scheduled within the inner loop. New schemes implement [`IterationSchemeInterface`](../../api/Distributed_Design_Optimizer/coordination/innerloop_iterationscheme/IterationSchemeInterface.md) (`run_innerloop_jobs_multiprocessing()`, the `print_*` hooks). Existing schemes include various `Parallel*` and `Sequential*` strategies.
- [`updatecouplingparametermethod/`](../../api/Distributed_Design_Optimizer/coordination/updatecouplingparametermethod/index.md) â€” how penalty weights and Lagrange multipliers are initialized and updated. New update rules implement [`UpdateCouplingParameterMethodInterface`](../../api/Distributed_Design_Optimizer/coordination/updatecouplingparametermethod/UpdateCouplingParameterMethodInterface.md) (`validate_inputs()`, `update_state()`, the `print_*` hooks). Existing rules include `UpdateCouplingParameterMethod_AdaptiveWeights`, `_AugLagMultipliersAdaptiveWeights`, `_AugLagMultipliersFixedWeights`, `_SubgradientMultipliers`, `_NoOp`, and others.

## 5. Implementing the coordination method entry point

Finally, everything is tied together in the [`coordinationmethod`](../../api/Distributed_Design_Optimizer/coordination/coordinationmethod/index.md) package with a `<Method>` class subclassing [`CoordinationMethodBasis`](../../api/Distributed_Design_Optimizer/coordination/coordinationmethod/CoordinationMethodBasis.md) and implementing [`CoordinationMethodInterface`](../../api/Distributed_Design_Optimizer/coordination/coordinationmethod/CoordinationMethodInterface.md). This is the class the user selects as `_coordinationmethod` in their `InputFile` (see [Tutorial > Problem Definition and Algorithm Execution](../problem-definition-and-algorithm-execution/index.md#3-defining-the-mainpy-and-inputfilepy)).

Its constructor receives all method-specific hyperparameters available for the user to choose. This may include some strategies chosen in [Section 4](#4-reusing-or-defining-convergence-iteration-scheme-and-update-classes).

**Interface methods to implement** (see [`CoordinationMethodInterface`](../../api/Distributed_Design_Optimizer/coordination/coordinationmethod/CoordinationMethodInterface.md)):

- `validate_inputs()`, together with `get_IterationScheme()`, `get_AllowedIterationSchemes()`, `get_RecommendedIterationSchemes()`, and `get_UnrecommendedIterationSchemes()`. This mirrors the `_allowed*`/`_recommended*` validation pattern recommended for `LocalSubSystem<Method>` in [Section 3](#3-defining-the-coordination-specific-subsystem-classes), applied at coordination-method level for method specific hyperparameters chosen by the user in their `InputFile`.
- `createSubSystems(id_list, level_list, neighborid_list, ...)` â€” build the list of `LocalSubSystem<Method>` instances ([Section 3](#3-defining-the-coordination-specific-subsystem-classes)), one per subsystem, wiring in their `CouplingParameters<Method>` ([Section 2](#2-defining-the-middlelevel-and-couplingparameters-classes)) and the convergence/update strategies of [Section 4](#4-reusing-or-defining-convergence-iteration-scheme-and-update-classes).
- `createControllerSubSystem(subsystemsIn)` â€” build the `ControllerSubSystem<Method>` that coordinates the local subsystems, or return `None` when the method has no controller ([Section 1](#1-casting-the-novel-distributed-optimization-method-into-the-unified-algorithmic-structure)).
- `createMiddleLevel(idparent, idchild, multiprocessing_lock)` and `createControllerMiddleLevel(...)` â€” build the shared `MiddleLevelDataStorage<Method>` interface storage ([Section 2](#2-defining-the-middlelevel-and-couplingparameters-classes)) for information exchange among local subsystems and with the controller (if existing). The latter returns `None` when there is no controller.
- `get_Convergence_Indicator_Innerloop()`, `get_Convergence_Indicator_Outerloop()` â€” return the inner- and outer-loop convergence indicator factories chosen in [Section 4](#4-reusing-or-defining-convergence-iteration-scheme-and-update-classes).
- `centralized_prepare_updateCouplingParameters(subsystemsIn)` â€” perform any method-specific *centralized* operation on the coupling parameters after the inner loop completes and before the decentralized *"Update relevant coupling parameters"* hooks of [Section 3](#3-defining-the-coordination-specific-subsystem-classes); leave it a no-op for fully decentralized methods.
- `print_startup_summary()`, `print_termination_summary()`, and `print_beginning_of_centralized_prepare_updateCouplingParameters()` â€” print the method configuration at start-up and termination, and a banner before the centralized preparation step.

## 6. Reusing an existing method without the full tutorial

Not every novel distributed optimization method requires all building blocks mentioned throughout this tutorial. Because the framework is composed of interchangeable parts, many variations reuse most of an existing method and only replace a single component:

For example, to run standard ALC with a different scheme for updating the multipliers and weights, or with a different inner-/outer-loop convergence criterion, only those classes in [Section 4](#4-reusing-or-defining-convergence-iteration-scheme-and-update-classes) are defined and passed to the existing [`ALC`](../../api/Distributed_Design_Optimizer/coordination/coordinationmethod/ALC.md) coordination method and [`LocalSubSystemALC`](../../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemALC.md) â€” everything else remains untouched.
