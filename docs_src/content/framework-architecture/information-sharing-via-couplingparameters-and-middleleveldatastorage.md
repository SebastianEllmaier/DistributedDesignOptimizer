# Information Sharing via CouplingParameters and MiddleLevelDataStorage

Two [`LocalSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) instances exchange relevant information through a pairwise-shared resource [`MiddleLevelDataStorageBasis`](../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelDataStorageBasis.md) instance. Every coordination method seeks to satisfy the pairwise coupling constraints between two [`LocalSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) instances (recall [Categorization and Selection of Suitable Solution Approaches](../distributed-optimization-for-multidisciplinary-design/categorization-and-selection-of-suitable-solution-approaches.md)). For this reason, the [`MiddleLevelDataStorageBasis`](../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelDataStorageBasis.md) between them holds information on `_mappedresponses` $^{i}_{j}$sym:H, `_couplingvariable` $^{i}_{j}$sym:h, `_shareddesignvariable` $^{i}_{j}$sym:z and `_targetshareddesignvariable` $^{i}_{j}$sym:z_{t} as illustrated below. Depending on the specific coordination method, additional information may be exchanged between subsystems.

Similarly, there exists a single [`MiddleLevelDataStorageBasis`](../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelDataStorageBasis.md) instance between a [`LocalSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) instance and a [`ControllerSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/ControllerSubSystemBasis.md) as illustrated below.

<iframe src="../MiddleLevelDataStorage_LocalSubSystemBasis_ControllerSubSystemBasis.drawio.html" width="100%" height="500" style="border:none;" allowfullscreen></iframe>

Each coupling therefore has two complementary representations. The [`MiddleLevelDataStorageBasis`](../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelDataStorageBasis.md) instances described above are the **shared interface storage** through which neighboring subsystems exchange coupling information; because the innerloop runs each subsystem in its own process (via `multiprocessing`), this shared storage is the mechanism by which information crosses process boundaries. Its counterpart is the *subsystem-local* view of each coupling, held in the [`couplingparameters`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/index.md) package: every [`LocalSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) keeps a list of coupling-parameter instances — one per pairwise coupling with a neighbor, each inheriting from [`CouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersBasis.md) — and copies values to and from the shared middlelevel coupling object inside the middlelevel, which always inherits from [`MiddleLevelCouplingBasis`](../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelCouplingBasis.md).

Both the middlelevel coupling class and the subsystem-local coupling-parameter class follow the same endpoint-dependent split. A coupling **between two [`LocalSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) instances** uses the richer [`SubSysMiddleLevelCouplingBasis`](../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md) (middlelevel) and [`SubSysCouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md) (subsystem-local), which extend [`MiddleLevelCouplingBasis`](../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelCouplingBasis.md) and [`CouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersBasis.md) respectively with the four standard coupling quantities (`_mappedresponses`, `_couplingvariable`, `_shareddesignvariable`, `_targetshareddesignvariable`). A coupling **between a [`LocalSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/LocalSubSystemBasis.md) and a [`ControllerSubSystemBasis`](../api/Distributed_Design_Optimizer/subsystem/ControllerSubSystemBasis.md)** does *not* use either richer class; because such a coupling is generally asymmetric, it instead splits into directional subclasses inheriting directly from `MiddleLevelCouplingBasis` / `CouplingParametersBasis`: [`LocalToController_MiddleLevelCouplingBasis`](../api/Distributed_Design_Optimizer/middlelevel/LocalToController_MiddleLevelCouplingBasis.md) / [`ControllerToLocal_MiddleLevelCouplingBasis`](../api/Distributed_Design_Optimizer/middlelevel/ControllerToLocal_MiddleLevelCouplingBasis.md) at the middlelevel, and [`LocalToController_CouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/LocalToController_CouplingParametersBasis.md) / [`ControllerCouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/ControllerCouplingParametersBasis.md) at the subsystem-local level.

The complete inheritance structure of both hierarchies is shown on [`middlelevel`](../api/Distributed_Design_Optimizer/middlelevel/index.md) and [`couplingparameters`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/index.md) API reference pages.

Each subsystem exchanges coupling information with its neighbors through the shared [`MiddleLevelDataStorageBasis`](../api/Distributed_Design_Optimizer/middlelevel/MiddleLevelDataStorageBasis.md) instances, with both directions protected by a `multiprocessing` lock: reads via [`SubSystemBasis.CopyFromMiddleLevel()`](../api/Distributed_Design_Optimizer/subsystem/SubSystemBasis.md) and writes via [`SubSystemBasis.CopyToMiddleLevel()`](../api/Distributed_Design_Optimizer/subsystem/SubSystemBasis.md).

By convention the coupling-parameter attributes mirror the naming of the matching [`SubSysMiddleLevelCouplingBasis`](../api/Distributed_Design_Optimizer/middlelevel/SubSysMiddleLevelCouplingBasis.md) class. In addition, each [`SubSysCouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/SubSysCouplingParametersBasis.md) holds a set of `_copy_*` attributes that store the data *pulled from the middlelevel* (i.e. the neighbor's values). The mapping between the two is realized by the [`CouplingParametersInterface`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersInterface.md) methods, of which a concrete coupling class must supply the two copy procedures:

- `CopyFromMiddleLevelCoupling(middlelevelcouplingIn)` — read the neighbor's shared values out of the middlelevel into the local `_copy_*` attributes.
- `CopyToMiddleLevelCoupling(middlelevelcouplingIn)` — write this subsystem's own values into the middlelevel for the neighbor to read.

The other two interface methods are largely handled by the base class: `get_ID()` is **already implemented** in [`CouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersBasis.md), where it returns the stored `_id` (the identifier of the neighboring subsystem), and `update_state(other_coupling)` — the `multiprocessing` state transfer that moves numerical values from a copy returned by a worker process back onto the original object without changing its memory address — already covers `_id` in the base and only needs extending when a subclass adds numerical attributes.

A key design point is that a [`CouplingParametersBasis`](../api/Distributed_Design_Optimizer/subsystem/couplingparameters/CouplingParametersBasis.md) subclass may hold information that is **never written to the shared middlelevel** — it stays local to the subsystem but remains associated with a specific neighbor. What is and is not communicated is decided entirely by `CopyToMiddleLevelCoupling()` and `CopyFromMiddleLevelCoupling()`.
